# 설계안: 모든 열을 고유키로 — 표기는 사전에, 이름은 `fields.json` 한 곳에

상태: **구현 완료**. 왜 그 모양인지는 `decisions.md`의 D39에 있고, 이 문서는 열거한 표와
열한 판에 걸친 설계 과정을 남긴다 — 어떤 선택지가 왜 버려졌는지 되돌아볼 자리다.
적는 날: 2026-10-22

여섯 차례 감사받아 치명적 결함 열다섯이 나왔고, 사용자가 결정 아홉을 내렸다.
**7·8판에서 코드가 열 이름을 해석하는 자리를 전부 없앴다**(§1.1·§4.3) — 그 해석이
감사 지적 여섯 건의 발원지였다.
바뀐 자리는 §12에 적어 둔다.

---

## 1. 원칙 — 추론하지 않는다

**프로그램이 열을 추론할 이유가 없다.** 머리글이 사전과 맞으면 읽고, 맞지 않으면
`extra`로 따로 빼되 필터를 걸 수 있게 둔다. 그것이 전부다.

- 조합 이름을 과목으로 **분해해 재조립하지 않는다**(「합성 정규화」, §5).
- 사전에 **없는 표기를 미리 넣지 않는다.** 본 것만 넣는다(§6 — CLAUDE.md의 §6).
- 뜻이 확인되지 않은 두 표기를 **합치지 않는다.** 남겨 두는 쪽이 낫다(§5).
  **사람이 확인해 주면 합친다** — 사전은 사람이 확인한 답을 적어 두는 곳이다(§4의 정신).

### 1.1 코드가 열 이름을 해석하는 자리를 없앤다

**「나누는 기준」이라는 것 자체가 코드가 열 이름을 해석하고 있다는 뜻이다.**
우리는 이 진학 프로그램들의 엑셀 양식을 **알고 있다.** 그러니 해석하는 것이 아니라
**미리 사전에 정의해 둔다.** 이것이 §1의 일반형이고, 아래 모든 수정의 근거다.

해석하는 자리를 전수로 찾았다. 여섯이다.

| 자리 | 지금 | 바뀐 뒤 | 어디 |
|---|---|---|---|
| `student.js:315` | `label.includes('(')`로 반영비 변형을 구분한다 | 사전의 `primary` | §4.3 |
| `student.js:314` | `['전교과','전과목','전교과목']`을 박아 두고 `startsWith` | 사전의 순서 | §4.3 |
| `student.js:256` | `AREA_ORDER` 배열 | 사전의 `areas` 순서 | §4.4 |
| `registry.js:249` | `/^gpa\.(전교과|전과목)$/` | 사전의 `default` | §4.3 |
| `registry.js:68` | 키를 쪼개 라벨을 만든다 | 사전의 `label` | §8-5 |
| `isKnownFieldKey` | 글자 모양을 정규식으로 본다 | 사전의 키 집합 소속 | §4.3 |

**해석을 남기는 자리는 둘뿐이고, 둘 다 「모르는 열」을 다루기 때문이다.**

- **`isIdentityLabel`**(`buildRecords.js:120`) — 해석하지 못한 열을 `extra`로 보존할 때
  사람을 특정하는 이름을 걸러낸다. 토큰 **포함** 검사라 느슨하고, **느슨해야 한다** —
  대상이 **열거할 수 없는 미지의 열**이고, 틀렸을 때 손해가 §1 위반(개인정보 유출)이라
  과하게 잡는 쪽이 옳다. **이 그물을 한정하지 않는다.**
- **`scoreLabel`의 `affix`·`partial`**(스칼라 열) — 사전에 없는 **다른 프로그램의**
  양식을 만났을 때의 느슨한 그물이다(D18의 주 경로). 임계값과 값 교차검증이 그것을
  지킨다. 아는 양식은 `exact`로 맞으므로 이 경로를 타지 않는다.

**둘의 공통점이 기준이다. 대상이 미지일 때만 해석하고, 아는 양식은 사전에 적어 둔다.**

**경계를 분명히 해 둔다 — 「해석」은 엑셀에서 온 글자를 보는 것만 말한다.**
점으로 이은 **우리 키의 접두사 구조**를 읽는 것(`groupOf`가 `gpa.`를 보고 내신 묶음에
넣는 것, `buildRecords`가 키로 값 갈래를 정하는 것)은 해석이 아니다 —
**그 구조는 우리가 만들었다.** 우리가 만든 파생 키(`outcome`·`stage1Passed`·`registered`)
와의 비교도, 묶음(`group`)으로 분기하는 것도, **값**을 보는 것도 해석이 아니다.
이 경계가 없으면 다음 사람이 `groupOf`까지 걷어내려 드는데,
**그것이 내신 열을 내신 묶음에 넣는 장치다**(`registry.js:46-49`).

## 2. 확인된 사실

열 이름이 달라도 같은 열로 모이는 장치가 **절반만** 있다.

| 갈래 | 고유키 ← 표기들 | 어디에 |
|---|---|---|
| 스칼라 열 (대학명·이름·최종단계…) | **있다** | `field-synonyms.json` |
| 결과 **값** (합격·합·충원합격) | **있다** | `outcome-vocab.json` (D10) |
| 수능 **항목** (과목·표점·백분위·등급) | **있다** | `section-anchors.json` |
| 내신 **조합** (국영수사·국수영사) | **없다** | 머리글 글자가 그대로 키 |
| 내신 **단일 과목** (국어·영어·…) | **없다** | 조합과 같은 경로 (§4.2) |
| 수능 **영역** (국어·탐구1·…) | **없다** | 머리글 글자가 그대로 키 |
| 해석 못 한 열 (`extra`) | 없다 (**의도된 것**) | §4.7 |

키를 만드는 자리는 두 줄이다.

```js
// resolveColumns.js:188
return whole ? `gpa.${combo}` : `gpa.${combo}(${ratio})`;
// resolveColumns.js:197
return `suneung.${area}.${part}`;   // part만 사전을 거친다
```

`combo`와 `area`는 사전을 거치지 않은 머리글 글자다.

### 2.1 나뉨 — 지금 당장 일어나는 일

동봉 프로파일 5장의 내신 고유키는 **41개**다. 조합 종류로는 **17개**인데, 실제 조합은
**13개**다(단일 과목 5개 + 조합 8개, §4.1).

| 같은 뜻 | 나뉜 키 |
|---|---|
| 전과목 평균 | `gpa.전교과` (대교협·예시) · `gpa.전과목` (센진학) |
| 국·수·영·사 | `gpa.국영수사` (대교협 2025·2026) · `gpa.국수영사` (대교협 2027·센진학) |
| 국·수·영·과 | `gpa.국영수과` (대교협 2025·2026) · `gpa.국수영과` (대교협 2027·센진학) |

**대교협 자료와 센진학 자료를 함께 올리면 내신 열이 하나도 겹치지 않는다.**

재현했다. 2025년 자료(`국영수사`/`대학명`/`최종단계`/`합격`)와 2026년
자료(`국수영사`/`대학이름`/`합불여부`/`합`)를 함께 불러오면:

```
지원 그룹:  univ(2행)  dept(2행)  final(2행)  outcome(2행)     ← 모였다
내신 그룹:  gpa.국영수사(1행)   gpa.국수영사(1행)              ← 나뉘었다
```

### 2.2 피해의 모양

§5가 말하는 **조용히 틀리는 값**이다. 나뉘어도 화면은 멀쩡하다.

- 필터·축에 두 이름이 따로 뜨고, 어느 쪽을 선택해도 그 해 자료만 나온다.
  **다른 해가 빠졌다는 표시가 없다.**
- 평균·분포가 한 해 것만으로 계산된다. 숫자는 그럴듯하다.
- 한 학생 카드에 같은 조합이 두 칸으로 나온다.
- **기본 내신 열이 글자 순서로 뽑힌다.** `registry.js:249`가
  `/^gpa\.(전교과|전과목)$/`를 `find`로 찾는데, 레지스트리는 라벨 `localeCompare`로
  정렬되어 있다. 두 표기가 함께 있으면 **어느 쪽이 대표가 될지 사전순이 정한다.**
  자료가 아니라 글자가 기본값을 선택한다.

### 2.3 가짜 수능 영역이 만들어진다

영역 이름도 날것이라, **사전에 없는 열이 수능 영역으로 둔갑한다.** 재현했다 —
수능 구역 뒤에 `총점평균`(값 2.3·3.5) 열을 끼우면:

```
수능으로 잡힌 키: suneung.한국사.grade, suneung.국어.grade, suneung.총점평균.grade
미해결: (없음)
```

**경고 하나 없이 영역이 생겼다.** 값 교차검증도 통과한다(등급 범위에 들기 때문이다).
`findSections`의 `namesAScalar` 방어는 침입한 열 이름이 **스칼라 사전에 있을 때만** 듣는다.

이것이 수능 영역 사전의 진짜 근거다 — **이미 열려 있는 구멍을 막는 일**이다.
§6(미리 만들지 않는다)에 걸리지 않는다.

### 2.4 왜 이렇게 됐는가 — 그리고 한 파일 안에서도 흔들린다

의도였다. `fields.json`:

> `"note": "반영 조합마다 열이 하나씩 있다. 조합 이름은 학교·프로그램마다 다르므로 자유 문자열로 둔다."`

**그 전제가 틀렸다.** 조합이 다른 것이 아니라 **같은 조합의 표기가 다르다.**

가장 센 증거는 `kcue-2027` **한 파일 안**에 있다.

```
gpa.국어  gpa.영어  gpa.수학  gpa.사회  gpa.과학  gpa.전교과
gpa.국영수사/과   gpa.국영수   gpa.국수영사   gpa.국영사   gpa.국수영과   gpa.수영과
          ^^^^           ^^^^        ^^^^
          영-수 순       영-수 순    수-영 순
```

한 프로그램의 **한 번의 내보내기** 안에서 `국영수`(영-수)와 `국수영사`(수-영)가 함께
있다. 양식을 만든 쪽도 표기를 통일하지 않았다는 뜻이다 —
**「순서만 다른 것은 짐작이 아니다」가 추론이 아니라 관찰이다.**

## 3. 목표와 비목표

**목표**

1. 같은 뜻의 열은 어느 양식에서 왔든 **한 고유키**로 모인다.
2. 화면에 보이는 이름은 **`fields.json`이 정한 대표 표기 하나**다. 어느 파일을 먼저
   올렸는지, 사전 목록의 순서가 어떻든 바뀌지 않는다.
3. 모르는 열은 **모른다고 남는다** — `extra`, 그리고 **두 경로 모두**가 그 사실을 알린다.
4. 새 표기 대응은 **사전에 낱말 하나 추가**로 끝난다(§4).

**비목표**

- `extra`를 모으지 않는다. `extra`는 「우리가 모른다」는 뜻이고, 거기서 이름이 비슷한
  것끼리 합치는 것이 바로 추론이다. `비고`와 `특기사항`은 따로 남는다.
- 값을 고치지 않는다. 이 설계는 **열이 어디로 모이는가**만 다룬다.
- 보관소 이주를 만들지 않는다 (§6).

## 4. 설계

### 4.0 사전의 집 — `fields.json`이 유일한 정본

**대표 표기는 `fields.json`에만 있다.** 나뉠 자리를 두지 않는다.

| 파일 | 지는 것 |
|---|---|
| `fields.json` | 개념이 존재한다 + **대표 표기(`label`)** + `type`·`group`·`required` |
| `field-synonyms.json` | 그 개념을 사람들이 이렇게 적는다 — **표기 목록만** |
| `section-anchors.json` | 구역 구분 — **구역 판정에 쓰는 표기는 여기 남는다**(§4.6) |
| `outcome-vocab.json` | 값의 뜻 |

스칼라는 이미 이 모양이다(`fields.json`의 `label`이 곧 대표 표기이고 `registry.js:14`가
거기서 읽는다). 그래서 **스칼라 사전에는 손댈 것이 거의 없다.** 내신 조합과 수능 영역을
같은 모양으로 맞추는 것이 이 설계의 일이다.

**기존 모양을 깨지 않고 더한다.** 이것이 중요하다 — `repeating.suneung.parts`와
`partTypes`는 코드가 읽고 있다.

```js
const SUNEUNG_PARTS = new Set(fields.repeating.suneung.parts);  // profile.js:32 — 문자열 배열
const PART_TYPE = fields.partTypes;                              // buildRecords.js:17
```

`parts`를 객체 배열로 바꾸면 `SUNEUNG_PARTS.has('grade')`가 거짓이 되어
**동봉 프로파일 5장이 전부 거절된다.** `partTypes`를 흡수하면
`typeOf('suneung.국어.grade')`가 `'text'`가 되어 **수능 등급·백분위·표점이 글자로
저장되고 범위 필터·정렬·축이 조용히 죽는다.** 그래서 **둘은 그대로 두고 라벨만 더한다.**

**조합 사전의 정본은 §4.3의 표다 — 29개 키, 받는 이름 65개.** 아래 두 블록은 **항목의
모양**을 보이는 것이고, 전체를 두 곳에 베껴 두지 않는다. 베껴 두면 한쪽만 고쳐지는데
그것이 이 설계가 없애려는 바로 그 모양이다. **§8-2는 §4.3의 표를 보고 사전을 만들고,
검사 3의 짝도 그 29개 위에서 돈다** — 조합 8개 위에서 돌면 **통과하면서** 반영비
변형에 라벨이 없는 상태를 승인하고, 4단계에서 `isKnownFieldKey`를 집합 소속 판정으로
바꾸는 순간 **날것 41가지 중 30가지가 거절되어** kcue 3장과 senjinhak이 통째로 떨어진다.

### 4.1 합치기의 선 — 이것이 설계의 핵심이다

**과목 토큰의 다중집합이 같고 순서만 다른 표기만 합친다.
토큰이 늘거나 줄거나 `/`가 끼면 합치지 않는다 — 사람이 확인해 주기 전까지는.**

| 합친다 | 왜 |
|---|---|
| `국영수사` ≡ `국수영사` | 토큰 {국,수,영,사}가 같다. **표기 순서 문제**다 (§2.4의 관찰) |
| `국영수과` ≡ `국수영과` | 같다 |
| `국영수` ≡ `국수영` | 같다 |
| `전교과` ≡ `전과목` ≡ `전교과목` | 「전체」를 뜻하는 동의어. `section-anchors.json`과 `registry.js`가 이미 동의어로 다룬다 |

| 합치지 않는다 | 왜 |
|---|---|
| `국영수사/과` ↮ `국수영사과` | **반영 과목 수가 다르다.** 앞은 4과목(사·과 택일), 뒤는 5과목 전부 (§4.1.1) |

**`국영수사과`는 사전에 넣지 않는다.** 토큰 다중집합으로는 `국수영사과`와 같아 이 선에
걸리지만, **§8-3이 그 표기를 저장소에서 지운다** — 유일한 출처가 우리 예시 양식이기
때문이다(§4.1.1). 지운 뒤 사전에 남겨 두면 어느 실제 양식에도 없는 표기가 되어
§1의 「본 것만 넣는다」를 문장 그대로 어긴다. 더구나 거기에는 「`/`가 없으면 5과목」이라는
**뜻에 대한 단정**이 붙는다. §2.4가 보인 것(한 프로그램이 한 파일 안에서도 표기를
통일하지 못한다)에 비추면, 어떤 양식이 **택일 조합을 `국영수사과`로 적을** 가능성을
배제할 근거가 없다. 그때 그 열은 5과목 열로 **조용히 합쳐지고 화면은 멀쩡하다.**
넣지 않으면 그 양식은 `extra`로 가서 사람에게 묻는다 — 설계가 원하는 동작이다.

**순서만 다른 것은 짐작이 아니다.** 「국영수사」와 「국수영사」가 다른 조합일 수는 없고,
한 파일 안에서 두 순서가 섞여 있는 것을 보았다(§2.4).
**반영 과목 수가 다른 것을 합치는 것은 값을 섞는 일이다.** 섞이면 한 열로 보이면서
값이 틀린다 — **나뉘어 있는 지금보다 나쁘다.**

이 선을 그으면 내신 키가 **41개에서 29개로**, 조합 종류는 **17개에서 13개로** 줄어든다.
반영비 변형이 조합마다 3~5개씩 붙어 있어 조합을 합쳐도 키 수가 크게 줄지는 않는다.
이득은 「숫자가 줄어든다」가 아니라 **「같은 조합이 한 열에 모인다」**다.

#### 4.1.1 두 조합의 뜻 — 사용자가 확정했다

| 키 | 표기 | 뜻 |
|---|---|---|
| `국수영사과택일` | 대교협 `국영수사/과` | **4과목 반영** — 사회와 과학 중 하나 |
| `국수영사과` | 센진학 `국수영사과` | **5과목 전부 반영** |

이것은 **사람이 확인해 준 답**이므로 사전에 적는다. 프로그램의 추론이 아니다.

**근거 하나는 저장소와 어긋난다 — 적어 둔다.** 「대교협에 `국수영사과` 필드와
`국수영사/과` 필드가 각각 있다」를 근거로 들으셨는데, 동봉 프로파일 3장을 세어 보면
**대교협 양식에는 `국영수사/과` 하나뿐이고 5과목 전부 반영 열이 없다.**


(`sampleWorkbook.js:76`). 그 표기를 대교협 것으로 기억하기 쉬운 자리이고, 그래서
§8 3단계에서 **생성기를 고친다** — 우리가 만든 자료가 사전의 근거가 되어서는 안 된다.

결론은 바뀌지 않는다. `/`가 택일의 표시라는 판단은 그 자체로 서고, 반영 과목 수가 다른
두 조합을 따로 두는 쪽이 §5에 맞다. 다만 **근거가 저장소에서 확인되지 않는다는 사실을
남겨 둔다** — 뒷사람이 이 결정을 다시 확인할 때 필요하다.

### 4.2 내신 단일 과목 열 — 조합과 같은 경로다

`국어`·`영어`·`수학`·`사회`·`과학` 한 과목짜리 열도 **`gpaKeyOf`가 똑같이 키를 만든다.**
확인했다: `GPA_SUBJECTS`는 `findSections`에서 **내신 구역의 왼쪽 끝을 넓히는 데만**
쓰인다(`resolveColumns.js:138`). 키를 만드는 경로가 따로 있는 것이 아니다.

> 1판은 「`section-anchors.json`이 이미 구분하고 있으니 그 경로를 쓴다」고 적었다.
> **그런 경로는 없다.** 그대로 구현하면 kcue 3장의 `gpa.국어`~`gpa.과학` 15개 키가
> 사전에 없는 키가 되고, `validateProfile`은 키 하나가 낯설면 **프로파일 전체를**
> 떨어뜨리므로(`profile.js:69`) **프로파일 세 장이 통째로 거절된다.**

### 4.3 반영비 — 규칙을 만들지 않는다. 열거한다

**이것이 설계에서 가장 크게 바뀐 자리다.** 1~6판은 반영비를 **읽는 규칙**을 만들려 했다 —
숫자를 뽑아 `/`로 잇고, 구분자를 통일하고, 전체 반영을 구별해고, 소수점을 받아 주고,
글자가 섞이면 물러나고. 감사 세 차례가 그 규칙의 버그를 고쳤다(`gpa.전교과(5)`를
지어내고, 전체 반영 열을 떨어뜨리고, `1.5/2`를 거절하고). **규칙 자체가 잘못이었다.**

**엑셀의 열 이름은 곧장 받아들인다. 정규화하지 않는다.** 그리고 우리는 이 양식들의
열이 무엇인지 **전부 알고 있다** — 프로파일이 그 답이다. 그러니 읽는 규칙을 둘 이유가
없다. **미리 계산해 사전에 적어 둔다.**

#### 사전의 단위는 머리글 이름 그대로다

머리글 이름은 `top`과 `sub`를 그대로 이어 적은 것이다 — `sub`가 있으면 `top(sub)`,
없으면 `top` 하나. 이것은 정규화가 아니라 **두 줄짜리 머리글을 한 이름으로 읽는 것**이고,
`buildHeaderLabels`가 이미 그 둘을 주고 있다.
**다만 그 함수가 함께 주는 `label`은 쓰지 않는다** — 그쪽은 `top`과 `sub`를
**가운뎃점**으로 잇는다(`한국사·등급`). 습관적으로 `.label`을 집으면 이름이 달라져
**41가지 전부가 미해결이 된다.** 쓰는 것은 `top`과 `sub`다. 사전은 그렇게 읽은 글자를 **그대로
열거한다.** 숫자를 뽑지도, 구분자를 바꾸지도, 전체 반영을 구별해지도 않는다.

두 머리글 모양이 같은 이름을 낸다. 오늘 이미 그렇다.

```
두 줄 (kcue-2026·2027)   top=전교과   sub=2/4/4   → 전교과(2/4/4)
한 줄 (kcue-2025)        top=전교과(2/4/4)        → 전교과(2/4/4)
```

`(100)`이 붙은 변형을 함께 열거하는 것이 **전체 반영 판정을 없앤다.** `wholeRatios`를
보고 괄호를 붙일지 말지 정하는 일이 사라지고, `전교과(100)`과 `전교과`가 **사전에서
같은 키로 간다.** 6판이 「순서를 적지 않으면 전체 반영 열이 미해결로 떨어진다」고 적은
그 함정이 아예 생기지 않는다.

**`(100)` 변형 18개는 동봉 프로파일에 이름으로 남아 있지 않다 — 그런데도 넣는다.**
오늘 코드가 전체 반영을 판정해 `100`을 지워 버리므로(`gpaKeyOf`) **프로파일이 그 이름을
증언할 수 없다.** 근거는 사람이 머리글을 직접 읽은 것이다 — kcue 2줄 머리글의 내신
열은 둘째 줄이 `100`이다(§2의 머리글). 이 설계는 §1의 「본 것만 넣는다」를 들어
`국영수사과`·`탐1`·`제2외`를 **빼낸** 문서이므로, 다음 사람이 같은 기준으로 `(100)`을
지울 수 있다. **지우면 전체 반영 열(전교과!)이 `extra`로 가고 `primaryGpaField`가
엉뚱한 조합을 대표 내신으로 올린다.** 지우지 않는 근거는 이것이다 — `sub`가 `100`인지
빈칸인지는 양식마다 다르고, **둘 다 받아도 같은 키로 가므로 틀릴 여지가 없다.**

`국영수사과`는 넣지 않는다 — 유일한 출처가 우리 예시 양식이고 §8-3이 그것을 고친다(§4.1).

#### `wholeRatios`는 4단계 뒤 쓰이지 않는다

`section-anchors.gpa.wholeRatios`(`["100","100%",""]`)를 읽는 곳은 `gpaKeyOf`
하나뿐이고(`resolveColumns.js:92·187`), 거기서 전체 반영 판정이 사라진다.
**4단계에서 그 항목과 `WHOLE_RATIOS`를 함께 지운다**(§6 — 쓰이지 않는 장치는 유지
비용만 남긴다). 지우지 않으면 다음 사람이 전체 반영 판정이 살아 있다고 읽고,
표에 `(100%)`가 없는 것도 설명 없는 비대칭으로 남는다 — `100%`는 그 목록에 있지만
**실제 양식에서 본 적이 없어 표에 넣지 않았다**(§1).

#### `isKnownFieldKey`는 집합 소속으로 끝난다

```
gpa 키가 유효한가  =  'gpa.' 뒤의 글자가 사전의 29개 고유키 중 하나인가
```

정규식도, 쪼개기도, 비 검증도 없다. **그리고 이것이 어떤 규칙보다 센 문지기다** —
프로파일 경로는 사전을 거치지 않으므로(§4.5 (나)) 거기 적힌 키를 검사하는 장치가
`isKnownFieldKey` 하나뿐인데, 이제 그 하나가 **사전과 정확히 같은 집합**을 본다.

#### 규칙을 버려서 함께 사라진 것들

1~6판이 쌓았고 감사가 고쳤던 자리 전부가 **존재하지 않게 된다.**

| 버린 규칙 | 그 규칙이 만들던 사고 | 어느 감사가 찾았나 |
|---|---|---|
| 숫자를 뽑아 `/`로 잇는다 | `(5등급)` → `gpa.전교과(5)` — **없는 반영비를 지어낸다** | 5차 |
| 구분자를 `/`로 통일한다 | `2:4:4`가 조용히 다른 키 — 본 적 없는 표기를 미리 다룬 것 | 2차 |
| 전체 반영을 구별한다 | 순서를 안 적으면 **빈칸·`100%` 열이 미해결로 떨어진다** | 6차 |
| 소수점을 받아 준다 | 허용 문자에서 빠뜨려 `1.5/2` 거절 — 같은 절과 모순 | 6차 |
| 비를 정규식으로 검증한다 | `gpa.전교과(100)`·`gpa.전교과()`가 유효 키가 된다 | 4차 |
| 조합을 `base`로 맞춘다 | `전교과(2/4/4)`가 `전교과`에 100점 — **가중평균이 대표 내신이 된다** | 4차 |

**규칙을 하나 두면 그 규칙의 예외를 찾는 일이 시작되고, 예외를 놓치면 조용히 틀린다.**
열거는 예외가 없다 — 목록에 없으면 `extra`로 가서 사람에게 묻는다(§5).

`5등급`·`탐1탐2`·`2015개정`·`1.5/2`·`2:4:4`·`주요교과`가 끼어든 머리글은 **전부 사전에
없으므로 `extra`로 간다.** 지어낼 길이 없다. 사람이 보고 뜻을 확인해 주면 그때 한 줄
더한다 — 그것이 §4가 말하는 「사람이 확인해 둔 답」이다.

#### 기본으로 보일 키도 사전이 정한다 — 글자를 보지 않는다

**학생 지원 모달에서 기본으로 보이는 내신은 사전이 `primary`로 표시한 키뿐이다.**
반영비가 붙은 키는 접힌 서랍에 들어간다. 그리고 **사전에 없는 고유키는 내신 묶음에
아예 뜨지 않는다** — 열거되지 않은 조합은 `extra`로 가므로(§4.3) 내신 묶음은
**사전의 29개 키와 정확히 같다.**

| | `primary` | 키 |
|---|---|---|
| 기본으로 보인다 | `true` | `전교과` · `국수영` · `국수영사` · `국수영과` · `국영사` · `수영과` · `국수영사과택일` · `국수영사과` · `국어` · `영어` · `수학` · `사회` · `과학` (13개) |
| 접어 둔다 | 없음 | 반영비가 붙은 16개 |

**이것이 `student.js`의 마지막 글자 판단을 없앤다.** 지금은 이렇다.

```js
// student.js:315
const 반영비붙음 = (entry) => entry.label.includes('(');
```

그리고 바로 위 주석(`student.js:303-313`)이 그렇게 한 이유를 적어 두었다.

> 나누는 기준은 **괄호**다. 조합 이름은 학교마다 다르므로 이름을 목록으로 박아
> 두면 다른 학교에서 통째로 빗나간다.

**그 전제가 이 설계로 사라진다.** 조합 이름이 자유 문자열일 때는 맞는 판단이었지만,
이제 사전이 그 목록이고 **정본이 하나**다(§4.0). 그래서 괄호를 보는 대신 사전에
물어본다 — `entry.primary`. 6판까지 작업 순서 6단계가 「이 판정은 없어지지 않는다 —
반영비는 열거할 수 없는 열린 값이라 사전으로 물어볼 수가 없다」고 적었는데,
**반영비를 열거하기로 한 순간 그 말이 틀렸다.** 이제 없어진다.

`조합순`(전교과를 앞에 두고 나머지는 라벨 사전순)도 **사전의 순서**로 바뀐다.
순서가 뜻을 나르게 되므로 `fields.json`에 그 사실을 적어 둔다(§7 검사 2).

**어느 키를 기본으로 보일지는 사전을 고쳐 바꾼다.** 괄호 유무와 맞아떨어지는 것은
오늘의 우연이고, 그것을 규칙으로 두지 않는다 — 규칙을 두면 또 예외를 찾게 된다(§4.3).

##### 카드 순서와 큰 글씨 첫 칸 — 못 박아야 하는 자리

`student.js:341`이 **첫 칸만** `text-3xl`로 키운다.

```js
보일내신.map((entry, index) => gpaCard(entry, index === 0))
```

그래서 순서가 **학생 지원 모달에서 가장 큰 숫자**를 정한다. 규칙 둘을 못 박는다.

1. **카드 순서는 `combos` → `subjects`다.** `fields.json`에는 `subjects`가 먼저
   적혀 있으므로(§4.0), 두 배열을 **파일 순서로 이어 붙이면 첫 칸이 `국어`가 된다.**
2. **큰 글씨 첫 칸은 `default` 키로 고정한다.** 순서에 맡기지 않는다 — 위에서
   「기본으로 보일 키는 사전을 고쳐 바꾼다」고 열어 두었으니, 그 날에도 대표 자리가
   흔들리지 않아야 한다.
   **구현은 `보일내신`을 정렬해 `default`를 맨 앞에 두고 `index === 0`을 그대로 쓴다** —
   오늘 코드 모양을 지키고, 아래 폴백이 자연히 따라온다.
3. **`default`가 채워지지 않은 양식에서는 `보일내신`의 첫 칸을 키운다.** 규칙 1 덕에
   그 칸은 조합이지 단일 과목이 아니다. `primary`가 하나도 채워지지 않은 양식(반영비만
   있는 양식)에서도 나열해 보이는 첫 칸이 커진다 — **오늘 동작이 그렇다.**
   이 폴백을 빼면 두 양식에서 **헤드라인이 사라져** 모달의 생김새가 양식에 따라 달라진다
   (`primaryGpaField`의 폴백과 같은 자리다, §8-6).

**이것이 `registry.js:240`이 이미 글로 경계해 둔 사고다.**

> 반영 조합 중 하나를 무작정 고르면 **`과학 6.88`처럼 그 학생을 대표하지 않는 값이
> 첫눈에 들어온다.**

첫 칸이 `국어`가 되면 상담 화면의 가장 큰 숫자가 **한 과목 성적**이 된다.
숫자도 화면도 멀쩡해서 상담하는 사람이 그것을 학생의 내신으로 읽는다(§5).

##### 접힌 서랍의 글귀도 사전 기준으로 바꾼다

지금은 「**반영비를 다르게 계산한** N개 더보기」(`student.js:348`)다. 구분하는 기준이
`primary`로 바뀌고, 검사 18은 「반영비 없음 == `primary`」를 **일부러 규칙으로 두지
않는다.** 오늘은 둘이 맞아떨어져 글귀가 참이지만, 반영비 없는 키의 `primary`를 떼는
날 그 열이 **「반영비를 다르게 계산한」 것으로 잘못 설명된 채** 서랍에 들어간다.
**「기본으로 보이지 않는 N개 더보기」**로 바꾼다 — 사전과 화면이 같은 기준을 말한다.

**반영비만 있는 양식의 대비는 그대로 둔다.** `primary` 키가 하나도 채워지지 않은
양식이라면 접을 것이 아니라 그게 전부이므로, 지금처럼 나머지를 나열해 보여 준다
(`student.js:325`의 `보일내신` 대비).

#### 구역 판정의 앵커 비교는 `base`를 계속 쓴다

조합 맞추기에서 괄호를 걷어내지 않는 것과 **다른 이야기다.** `findSections`는
`tops[i].base`로 앵커를 찾고(`resolveColumns.js:133·138`), 그쪽에서 `base`는 제 일을
한다 — `전교과(2/4/4)`의 `base`가 `전교과`라서 **한 줄 머리글에서도 내신 구역이 열린다.**
걷어내면 그 양식의 내신 열 전부가 미해결로 떨어지고, 기존 구역 판정 픽스처는 두 줄
머리글이라 **잡아 주지 않는다.**

**구역을 구분할 때는 괄호를 걷어내고, 조합을 맞출 때는 글자 그대로 본다.**
같은 낱말이 두 함수에서 반대 일을 하는 자리다.
### 4.4 수능 영역 — 열거하면 가짜 영역이 막힌다

근거는 §2.3이다. 동봉본 5장의 영역 **표기**는 우연히 전부 일치하므로 키는 하나도
바뀌지 않는다. 바뀌는 것은 **사전에 없는 이름이 들어올 때 걸린다**는 점이다.

`한문`·`탐구I`·`탐구①` 같은 미확인 표기는 **넣지 않는다**(§6). `제2외국어`와 `한문`이
수능에서 한 영역이라는 것은 알지만, `한문`이라 적힌 양식을 보기 전에는 넣지 않는다.

#### `국수영(탐1탐2)` — 오늘 등록한 프로파일에서 드러난 것

`kcue-2027`에 이 키가 있다.

```json
"suneung.국수영(탐1탐2).grade": 81
```

**수능 영역이 아니다.** 국·수·영·탐 등급의 **평균**, 즉 요약 값이다. 지금은 영역
이름이 날것이라 그대로 통과했지만(확인: `isKnownFieldKey` → `true`), 영역을 열거하면
떨어진다. **`extra`가 더 정직한 자리다** — 영역별 등급과 나란히 놓이면 「수능 등급
하나」로 집계될 수 있고, 그러면 분모가 조용히 틀어진다.

요약 값을 담을 개념(`suneungSummary.…`)은 **만들지 않는다.** 쓸 자리가 없다(§6).

조건 둘이 붙는다.

1. `kcue-2027`에서 그 줄을 빼는 일은 **`isKnownFieldKey`를 한정하는 그 커밋 안에서**
   해야 한다. 따로 가면 그 사이에 `bundled-profiles.test.js`가 깨진다.
2. **§4.5를 먼저 만들어야 한다.** 지금 구조에서 그 열은 「묻지도 않고」 `extra`가 된다.

### 4.5 프로파일 경로 — 미해결 보고가 없고, 사전도 거치지 않는다

**이 절이 설계에서 가장 중요하다.** 실제 대교협 파일은 프로파일 경로로 해석되므로
**이쪽이 본선이다.**

문제 둘. 확인했다.

**(가) 미해결을 계산하지 않는다.**

```js
// pipeline.js:98 — 프로파일 경로
unresolved: [],
// pipeline.js:294 — 경고
if (reading.source === 'names' && reading.unresolved.length > 0) { … }
```

사전에 없는 조합이 `extra`로 내려가도 **프로파일로 읽은 시트는 아무 말도 하지 않는다.**

**지금 바로 걸리는 일이 하나 있다.** 오늘 `kcue-2027`을 등록하기 전에는 그 파일이
이름 경로로 해석되어 「열 14개를 해석하지 못해 보존했습니다」가 떴다. 프로파일을 등록한
뒤에는 **같은 14개가 그대로 `extra`로 가는데 안내가 사라진다.** 열을 더 이해해서가
아니라, 프로파일 경로가 보고하지 않기 때문이다. 목표 3이 본선에서 성립하지 않는다.

**(나) 사전을 거치지 않는다. `isKnownFieldKey`가 유일한 문지기다.**

```js
// pipeline.js:91
const columns = match.profile.columns;   // 그대로 쓴다
```

`gpaKeyOf`는 **이름 경로에서만** 돈다. 즉 프로파일에 `gpa.국영수사`라고 적혀 있으면
**사전을 통째로 우회해 오늘의 나뉨이 그대로 되살아난다.** 그것을 막는 장치는
`isKnownFieldKey` 하나뿐이다 — §4.3이 그것을 한정해야 하는 이유이고, 검사 4가 동봉
프로파일을 훑어야 하는 이유다.

**할 일**: 프로파일 경로도 미해결을 계산한다 — 머리글 라벨 중 `columns`가 가리키지
않는 열을 모아 같은 모양으로 반환한다. 식별 열을 걸러 내는 처리(§1)는 이름 경로와
공유한다. 구현 가능함을 확인했다: `readSheetColumns(grid, match)`가 격자를 받고
`match.profile.headerRows`가 있으므로 `buildHeaderLabels` + `columns` 차집합으로 끝난다.
`ready` 판정은 `reading.source === 'profile' && reading.readable`(`pipeline.js:212`)이라
**미해결에 묶여 있지 않으므로** 이 단계가 `ready`를 뒤집는 연쇄도 없다.

### 4.6 구역 판정 표기는 `section-anchors.json`에 남는다

§4.0 표의 「구역 구분만」은 정확하지 않다. 거기 남는 것은 **표기 목록**이다.

```
section-anchors.gpa.anchors   = ['전교과','전과목','전교과목']        ≡ gpaCombos['전교과'].exact
section-anchors.gpa.subjects  = ['국어','영어','수학','사회','과학']   ≡ gpaSubjects 의 표기
section-anchors.suneung.parts = 과목·과목명·선택과목·표점·표준점수·백분위·등급
```

**옮기지 않는다.** 이 표기들은 「이 열이 어느 구역이냐」를 구분하는 데 쓰이고, 그 판정은
키를 만들기 **전에** 일어난다(D18). 역할이 다르므로 자리도 다르다.

**대신 두 곳이 어긋나지 않게 검사로 묶는다.** 한쪽만 늘면 피해가 크다 — 「전체」를
뜻하는 새 표기를 `gpaCombos`에만 더하면 `findSections`가 내신 구역 자체를 못 찾아
(`GPA_ANCHORS`는 `section-anchors`에서만 온다) **그 양식의 내신 열이 통째로 `extra`로
간다.** 1단계가 끝나 있으면 「열 n개 해석 못함」으로는 뜨지만, 내신 묶음이 화면에서
사라진 까닭은 아무 데도 적히지 않는다. 검사 10~12로 못 박는다.

### 4.7 `extra` — 그대로 둔다. 그리고 이미 필터가 걸린다

날것인 것이 설계다. **그리고 필터·정렬·축이 이미 된다.** 확인했다 — 레지스트리가
행에서 직접 만들어지고 필터가 레지스트리에서 나오기 때문이다(`filters.js:5`).
해석 못 한 두 열을 넣어 실행한 결과:

```
extra.최저학력기준 | 표시이름: 최저학력기준 | 값 있는 행: 2
extra.학교유형     | 표시이름: 학교유형     | 값 있는 행: 2
```

기존 테스트가 이미 덮는다(`analysis.test.js:84·105·110`).
**이 항목은 할 일이 없다.** 이름이 사람을 특정하는 열을 버리는 장치
(`fields.json`의 `identityLabels`, §1)도 그대로 둔다.

## 5. 하지 않는 것 — 합성 정규화

조합 이름을 과목으로 분해해 재조립하는 방식(`국영수사`→`{국,영,수,사}`→정렬).
**선택지가 아니다**(§1). 1판에서 내가 권했다가 철회했고, 사용자 결정으로 닫혔다.

기록을 위해 반례만 남긴다.

- **`국영수사/과`가 집합이 아니다.** 4과목 반영이다. 분해하면 `{국,영,수,사,과}`가 되어
  **5과목 전부 반영 조합과 같은 키**가 된다(§4.1.1).
- **`국수영(탐1탐2)`가 두 번째 반례다.** 분해기는 「국·수·영·탐 조합」으로 읽어 통과시킨다.

**다만 이 반례들은 열거 사전에도 똑같이 걸린다.** 손으로 섞어도 섞인 것은 섞인 것이다.
그래서 §4.1의 선이 필요하다 — 기각 사유로 쓸 수 있는 것은 「분해가 위험하다」가 아니라
**「반영 과목 수가 다른 것을 합치는 것이 위험하다」**다.

분해는 버리지 않고 자리를 옮긴다. 미해결 열을 사람이 지정하는 화면이 생기면, 거기서
「`국영수사`는 `국수영사`인 것 같습니다」를 **미리 채워 둔 빈칸**으로 보여 주면 된다 —
고3 년도 추론과 같은 취급이다(§2). **자동 적용은 하지 않는다.** 그 화면은 아직 없다(§6).

### 프로파일 추가는 답이 아니다

D18이 이미 기각했고 이번 건에도 답이 아니다. 프로파일은 열 **번호**를 묶어 두는
캐시다. 번호가 맞아도 키 이름이 나뉘면 열은 그대로 나뉜다 — **오늘 `kcue-2027`을
추가한 뒤에도 나뉘어 있는 것**이 그 증거다(§4.5 (나)).

## 6. 보관소 — 이주를 만들지 않는다

**배포 전이고 늘 초기화하므로 이주 경로를 만들지 않는다.** `DB_VERSION`도 올리지 않는다.
1판은 이주 방식을 길게 비교했는데, 쓰이지 않을 장치였다 — §6 위반이다.

사실관계만 남긴다. 배포 뒤에 키가 또 바뀌면 그때 판단할 거리다.

- 내신은 학생 레코드의 `gpa` 객체 안에 **조합 이름을 키로** 산다. 키가 바뀌면 묵은
  레코드는 옛 키를 그대로 들고 있다.
- **수능 저장소 주키는 `['sid', 'area']`**지만, §4.4대로 **영역 키는 하나도 바뀌지
  않는다.** 주키를 다시 쓸 일은 없다. (1판은 이 비용을 과대평가했고, 그 과대평가가
  「자료를 버리자」는 결론을 떠받치고 있었다.)
- 「데이터 초기화」는 `clearAll`과 `forgetView`를 **함께** 부른다(`main.js:802`).
  보관소와 화면 상태가 같이 지워지므로, 초기화하는 동안에는 아래 문제가 드러나지 않는다.

### 배포 뒤로 미루는 것 하나 — 저장된 화면 상태

`localStorage`의 화면 상태는 보관소와 따로 산다. 키가 바뀌면 `prefs.js`의
`pruneView`가 **옛 키를 쓰는 필터·정렬·열 선택을 말없이 버린다.**

```js
filters: view.filters.filter((filter) => known.has(filter.key))
```

필터가 사라지면 표가 **더 많은 행을 보여 주고**, 그 사실이 화면 어디에도 안 뜬다 —
§5가 말하는 모양 그대로다. 지금은 늘 초기화하므로 드러나지 않는다.
**배포 전에 다시 볼 자리로 `backlog.md`에 적어 둔다.**

## 7. 검사로 지킬 것

새 사전은 조용히 틀릴 수 있는 종류다. 다음을 테스트로 못 박는다.

**사전 자체**

1. **한 표기가 두 고유키에 들어가지 않는다. 그리고 고유키가 겹치지 않는다.**
   표기가 겹치면 어느 쪽으로 갈지 목록 순서가 정하고, **키가 겹치면 어느 `label`이
   이기는지 Map 생성 순서가 정한다** — 검사 1이 경계하는 바로 그 모양인데 3판까지
   키 쪽이 비어 있었다.
   **키 겹침은 `combos`와 `subjects`를 합쳐서 본다** — 둘은 다른 갈래지만 **같은 `gpa.`
   키 공간**에 떨어진다. (오늘은 겹치지 않는다: 키 **29개**, 받는 이름 **65개** 모두 중복 없음 — §4.3의 표.)
2. **모든 고유키에 `label`이 있고, 한 갈래 안에서 `label`이 겹치지 않으며,
   `label`에 괄호가 없다.** 겹치면 화면에 같은 이름의 두 열이 뜬다. 라벨의 괄호는
   `student.js:315`의 반영비 판정에 걸린다(§4.0) — 그래서 반영비 변형의 라벨은
   `국·수·영·사 2/4/4`처럼 **괄호 없이** 적는다.
   **키의 괄호는 반영비 접미사뿐이다** — `(<비>)` 모양으로 끝나는 것만 허용하고,
   그 안에는 괄호가 없다. 6단계가 반영비 판정을 `/\(.+\)$/.test(entry.key)`로 옮기므로
   다른 자리의 괄호는 그 판정을 어긋나게 한다.
   `areas`의 순서가 성적표 순서라는 것도 여기서 밝힌다.
3. **네 갈래를 **짝지어** 견준다.** 두 파일의 키는 이름 공간이 다르므로(`univ` vs
   `국수영사`) 짝을 명시하지 않으면 구현할 수 없다 — 전부를 `fields.scalars`에 견주면
   바로 실패하고, 갈래를 멋대로 정하면 **조합·영역을 빼놓고 통과한다.** 후자면 조합
   키에 `label`이 없어도 통과해 `fieldLabel`이 날것 키로 떨어지고 화면에
   `국수영사과택일`이라고 적힌다 — 목표 2가 깨진다.

   | `field-synonyms.json` | `fields.json` |
   |---|---|
   | `scalars` | `scalars` |
   | `gpaCombos` | `repeating.gpa.combos` |
   | `gpaSubjects` | `repeating.gpa.subjects` |
   | `suneungAreas` | `repeating.suneung.areas` |

   각 짝에서 **synonyms의 모든 키가 fields에 있고, fields에서 `derived`가 아닌 키는
   모두 synonyms에 있다.** 키 집합 **동일**로 적으면 오늘 상태에서 실패한다 — 차이는
   `cohortYear` 하나이고, 그것은 §2대로 **사람이 확정하는 파생 필드**라 머리글 동의어가
   있을 수 없다. `fields.json`에 `"derived": true`를 붙여 예외를 명시한다.

**사전과 코드·프로파일**

4. **동봉 프로파일의 모든 키가 사전에 있다.** `kcue-2027`의 `국수영(탐1탐2)`와
   kcue 3장의 단일 과목 열이 걸릴 자리다(3단계 전이라면 `sample-2026`의
   `gpa.국영수사과`도).
   **프로파일 경로는 사전을 거치지 않으므로 이 검사가 그 경로의 문지기다**(§4.5 (나)).
5. **어느 두 머리글도 한 키로 가지 않는다.** 검사 1의 역이다. 둘을 한 키로 묶는
   사전에서는 앞 열이 키를 차지하고 **뒤 열이 `extra`로 내려간다** — 내신 열 하나가
   내신 묶음에서 사라진다.

   **이 검사는 2단계에서 실행해야 하고, 7단계에서는 모양을 바꿔야 한다.**
   프로파일은 **머리글 글자를 보관하지 않는다** — 키와 열 번호, 그리고 일방향 지문뿐이다.
   지금은 **키가 곧 날것 머리글**이라 키로 대신 볼 수 있지만, **4단계에서 키가 정규
   키로 바뀌는 순간 그 대역이 사라진다.** 7단계에 그대로 두면 정규 키끼리 비교하는
   **반드시 통과하는 빈 검사**가 된다 — 이 설계가 내내 경계한 「없는 안전을
   통과시킨다」 그 자체다.
   - **2단계**: 동봉 5장의 날것 키로 한 번 실행해 결과를 주석에 남긴다(일회성 감사).
     **프로파일마다 따로 본다 — 같은 프로파일 안에서 두 키가 한 키로 가지 않는지만
     본다.** 서로 다른 프로파일의 키가 한 키로 모이는 것은 막으려는 것이 아니라
     **하려는 것**이다. 5장을 모아 실행하면 **충돌 11가지가 뜨는데 그것이 전부 이 설계가
     하려는 합치기다**(`국영수사`+`국수영사`, `전교과`+`전과목`, `국영수과`+`국수영과`와
     그 반영비 변형들). 2단계는 코드도 프로파일도 손대지 않은 시점이라 구현하는 사람
     앞에 놓인 유일한 「고칠 것」이 사전이고, 그러면 **가장 쉬운 탈출구가 합치기를
     되실행하는 것**이 된다 — §8-4가 경고한 것과 같은 함정이다.
     **오늘 실행한 결과: 같은 프로파일 안에서는 5장 모두 충돌 0.** 구현자가 자기 결과를
     견줄 기준이다.
   - **7단계**: `국영수사`와 `국수영사`를 **한 시트에** 둔 격자로 바꾼다. 뒤 열이
     조용히 사라지지 않고 **미해결로 보고되는지**를 본다. 검사 9와 한 몸이고,
     실제 양식이 둘을 함께 싣는 날 걸린다.
6. **`repeating.suneung.parts`가 문자열 배열로 남아 있고 `partTypes`의 키 집합과
   일치하며, `partTypes`의 값이 `number`/`text`뿐이다.**
   `profile.js:32`와 `buildRecords.js:17`이 그 모양에 걸려 있다(§4.0).
   값 검사가 없으면 엉뚱한 값이 들어가 `typeOf`가 `'text'`로 떨어져
   **수능 값이 글자로 저장된다** — 키 집합 검사를 통과한 채로 들어온다.
7. **`partLabels`의 키 집합이 `parts`와 일치한다.**

**동작**

8. **나뉜 양식이 한 열로 모인다.** §2.1의 실험을 **회귀 테스트로 남긴다.**
9. **해석하지 못한 열은 `extra`로 가고 미해결로 보고된다 — 두 경로 모두에서.**
   재는 것이 경로마다 다르다. 이름 경로는 「사전에 없는 조합」이고, 프로파일 경로는
   「프로파일이 가리키지 않는 열」이다 — 그쪽에는 사전에 없는 조합이 애초에 올 수 없다
   (검사 4가 금지한다). 이름 경로로만 쓰면 **없는 안전을 통과시킨다**(§4.5).
10. **`isKnownFieldKey`가 사전의 고유키 집합과 정확히 같은 것을 받는다.**
    열거 대상 41가지가 모두 29개 키로 가고, 사전에 없는 머리글
    (`전교과(5등급)`·`국수영(탐1탐2)`·`전교과(2:4:4)`·`전교과(1.5/2)`·`전교과(주요교과)`)은
    **하나도 키가 되지 않고 미해결로 보고된다** (§4.3). 규칙이 없으므로 이 검사가
    §4.3의 표를 그대로 지킨다.
11. **이름 매칭 경로와 프로파일 경로가 같은 답을 낸다** — 기존 검사를 새 키로 다시 돈다.

**사전 사이 (§4.6)**

12. `section-anchors.gpa.anchors`의 집합 **==** `gpaCombos['전교과'].exact`에서
    **전체 반영 변형(`전교과(100)`)을 뺀** 집합. 그 변형은 같은 키로 가는 덧붙임이라
    표지와 견줄 대상이 아니다.
    **`⊆`로 두면 §4.6이 막겠다고 적은 실패를 그대로 통과시킨다** — 「전체」를 뜻하는
    새 표기를 `gpaCombos`에만 더하는 것이 바로 사전 쪽이 커지는 방향이고, `⊆`는
    만족한다. 그러면 `findSections`가 내신 구역을 못 찾아 그 양식의 내신 열이 통째로
    `extra`로 가는데 까닭은 어디에도 적히지 않는다. 오늘 두 목록은 글자까지 같다.
13. `section-anchors.gpa.subjects`의 집합 == `gpaSubjects`의 표기 집합
14. `section-anchors.suneung.parts`의 **값** 집합 == `repeating.suneung.parts`의 집합
15. `section-anchors.suneung.anchors`(`한국사`) ⊆ `suneungAreas`의 표기.
    검사 12의 쌍둥이다 — 한쪽에서 `한국사`가 빠지면 **수능 구역을 여는 그 열 자체가
    `extra`로 간다.** 보고되므로 조용하지는 않지만, 12·13·14와 대칭을 맞춰 둔다.
    **12·13·14는 `==`, 15는 `⊆`인 비대칭은 의도다** — 「전체」 표기는 내신 구역을 여는
    **유일한** 표지라 양방향이 필요하고, 수능은 표지가 `한국사` 하나이고 영역은 일곱이라
    `==`가 성립할 수 없다. 적어 두지 않으면 다음 사람이 대칭을 맞추려 15를 `==`로
    바꾸고, 그러면 영역 여섯이 앵커에 없다고 검사가 터진다.

**기본 표시 (§4.3)**

16. **`primary`와 `default`는 사전에만 있고, 코드에 글자로 박힌 목록이 없다.**
    **범위는 §1.1의 여섯 줄이다** — 훑을 패턴 넷을 못 박는다:
    `includes('(')` · `AREA_ORDER` · `['전교과'` · `/^gpa\.`.
    「코드에 글자로 박힌 목록이 없다」로 넓게 두면 화면 글귀(한국어가 가득하다)와
    `registry.js:231`의 `defaultColumns`(우리 **논리 키** 목록이고 엑셀 이름이 아니다)
    까지 오탐한다.
    소스를 훑는 검사다(`tests/text-size.test.js`·`tests/terms.test.js`의 기계를 쓴다).
    **`src/`만 훑는다.** 그 기계는 `docs/`까지 보는데(`terms.test.js:126`,
    `prose.test.js:20`의 `EXTENSIONS`에 `.md`가 있다), **패턴 넷은 이 설계 문서와
    `decisions.md`가 전부 인용한다** — 범위를 한정하지 않으면 6단계에서 반드시 빨간불이
    된다. (또는 `EXEMPT`에 `docs/`를 넣는다. `decisions.md`는 이미 두 검사의
    `EXEMPT`에 있다.)
    **주석 예외 방식을 함께 쓴다** — §8-6이 고치라고 한 `student.js:303-313`의 주석은
    옛 기준(괄호)을 **인용**하므로 그 줄이 검사에 걸린다. `terms.test.js`의 줄 단위
    예외(`EXEMPT`)를 그대로 쓴다. 안 적으면 구현자가 자기 주석 때문에 빨간불을 보고
    **검사를 약하게 고치거나 주석을 지우는데, 그 주석이 괄호 판정의 부활을 막는
    장치다**(§8-6).
17. **`default: true`가 정확히 하나다.** 둘이면 필터·축의 기본 내신 열이 사전 순서로
    뽑히고, 없으면 기본값이 비어 화면이 내신 없이 열린다.
18. **`primary: true`가 하나 이상이고, 반영비가 붙은 키에는 없다.**
    오늘은 13개이고 모두 반영비 없는 키다. 「반영비 없음 == `primary`」는 **오늘의
    우연이므로 규칙으로 두지 않는다**(§4.3) — 그래서 이 검사는 `primary`가 반영비 키에
    붙지 않았는지만 보고, 그 역은 **규칙으로** 보지 않는다.
    **대신 오늘의 13개를 테스트에 글자로 박아 둔다.** 반영비 없는 키를 새로 더하며
    `primary`를 빠뜨리면 그 열이 **조용히 접힌 서랍으로 가는데**, 박아 두면 요란하게
    터지고 일부러 바꾸는 사람은 두 줄을 고치며 한 번 더 생각한다. 「미리 만드는 것」이
    아니라 **오늘 확인한 답을 적어 두는 것**이라 §6에 걸리지 않는다
    (`bundled-profiles.test.js`가 사실을 못 박는 방식).
19. **학생 레코드의 `gpa` 키가 전부 사전에 있다.** 내신 묶음이 사전과 정확히 같은
    집합임을 지킨다 — 사전에 없는 고유키는 내신 묶음에 뜨지 않고 `extra`로 간다.

## 8. 작업 순서

각 단계가 끝날 때 테스트가 통과해야 한다. 단계마다 따로 커밋한다.

1. **프로파일 경로의 미해결 보고**(§4.5 (가)). 사전과 무관하게 **먼저** 간다.
   지금 비어 있는 안전이고, 이것이 없으면 뒤 단계가 열을 조용히 `extra`로 보낸다.
2. **사전만 만든다** — `fields.json`에 `subjects`·`combos`·`areas`·`partLabels`·`derived`를
   **더하고**(`parts`·`partTypes`는 그대로 둔다, §4.0), `field-synonyms.json`에
   `gpaCombos`·`gpaSubjects`·`suneungAreas`를 더한다.
   **코드는 읽지 않는다** — 기존 모양을 깨지 않으므로 이것이 가능하다.
   검사 1·2·3·6·7·12·13·14를 먼저 둔다.
   **검사 5를 여기서 한 번 실행한다** — 프로파일 키가 아직 날것이라 이때만 검증력이
   있다(§7-5). 결과를 주석에 남긴다.
3. **예시 양식을 `국수영사`로 고친다** — `sampleWorkbook.js:76`의 `국영수사과`와
   `sample-2026.json`의 `gpa.국영수사과`. **머리글이 바뀌므로 지문을 다시 계산해
   프로파일에 넣는다**(`tests/sample.test.js:40·47·17`이 세 방향에서 잡아 준다).
   **`국수영사`로 선택하는 이유**: 정규 키와 글자가 같아 4단계 뒤에도 그대로이므로
   커밋 하나로 끝나고, **뜻이 확인된 조합**이라 체험 화면이 「확인되지 않은 조합」을
   대표 내신으로 내세우지 않는다. 우리가 만든 자료가 사전의 근거가 되지 않게 하는
   단계이기도 하다(§4.1.1).
4. **`gpaKeyOf`·`suneungKeyOf`가 사전을 거치게 한다. `isKnownFieldKey`를 사전의 고유키
   집합 소속 판정으로 바꾼다(§4.3). 같은 커밋에서 동봉 프로파일의 키를 정규 키로
   다시 적는다.**
   **이 셋은 쪼갤 수 없다.** 사전을 한정하는 순간 `bundled-profiles.test.js`가 깨진다.

   **규모를 밝혀 둔다 — 「한 줄 삭제」가 아니다.** 한정한 `isKnownFieldKey`를 동봉 5장에
   실행해 세어 보았다.

   ```
   kcue-2025        거절 15 / 67   (국영수사/과 ×4, 국영수, 국영수사 ×5, 국영수과 ×5)
   kcue-2026        거절 15 / 67   (같다)
   kcue-2027        거절  6 / 68   (국영수사/과 ×4, 국영수, suneung.국수영(탐1탐2).grade)
   senjinhak-2026   거절  1 / 26   (gpa.전과목)
   sample-2026      거절  1 / 32   (gpa.국영수사과 — 3단계가 이미 처리했다)
   ```

   **내신 키 37개 + 수능 요약 1개를 다시 적어야 한다.** `validateProfile`은 키 하나에
   프로파일 **전체**를 떨어뜨리므로(`profile.js:69`) 중간 상태가 없다 — 5장 중 4장이
   거절되고 kcue가 이름 경로로 떨어진다(kcue-2025는 머리글이 1줄이라 81열 중 33열만
   풀린다, D23). 검사 4·11이 잡으니 배포되지는 않지만, 규모가 적혀 있지 않으면
   **구현하는 사람이 여기서 막히고 가장 쉬운 탈출구가 `isKnownFieldKey`를 느슨하게
   되실행하는 것**이다 — 2판이 실제로 그 방향으로 적었던 자리다.

   **손으로 고치지 않는다. 사전으로 실행하는 일회용 스크립트로 표기→키만 바꾸고 열 번호는
   손대지 않는다.** 프로파일은 열 번호만 들고 있고 원본 머리글 글자는 들고 있지
   않으므로(지문은 일방향 해시), 손으로 고치다 `gpa.국수영사(2/4/4)`를 원래
   `국영수과(2/4/4)`가 있던 번호에 적으면 **그 열이 통째로 다른 조합으로 들어가고 값
   범위 검증도 통과한다**(둘 다 내신 1~9). 화면은 멀쩡하다 — §5가 말하는 그 모양이다.
   검사 1이 표기→키를 유일하게 정하므로 이 변환은 결정적이고, 디프로 눈검사가 된다.

   **테스트도 함께 손이 간다 — 내신 키·이름을 품은 파일이 열이다**: `analysis` ·
   `buildRecords` · `db` · `helpers/workbook` · `pipeline` · `profile` ·
   `resolveColumns` · `sample` · `table-align` · `table-window`.
   요란하게 깨지는 것은 **설계가 의도한 바**다(그래서 검사 4·11이 있다). 규모를 적어
   두는 것은 4단계 커밋의 크기를 미리 알리기 위한 것이다.
5. **표시 이름을 `fields.json`에서 끌어온다** — `fieldLabel`이 조합·영역·항목 키를
   `label`로 옮긴다. 그리고 **흩어진 이름 사본 셋을 그 한 곳으로 모은다**:
   `student.js:256`의 `AREA_ORDER`, `student.js:314`의 `전교과` 목록,
   `student.js:250`의 `선택과목` ↔ `registry.js:68`의 `과목`.
   `student.js:306`의 주석이 `국영수사과`를 예로 드는데, 3단계가 그 표기를 지우므로
   함께 고친다 — 물러난 말이 주석에 남으면 되살아난다(`tests/terms.test.js`가 밝힌 경로).
   **완료 조건 둘**:
   - `registry.js:68`과 `student.js:250`이 **둘 다** `partLabels`를 읽는다.
     한쪽만 옮기면 같은 항목이 표에서 `과목`, 카드에서 `선택과목`으로 남는다 — 지금 그대로다.
   - **`fieldLabel`은 키를 그대로 사전에서 찾는다 — 비 접미사도 키의 일부다.**
     `gpa.전교과(2/4/4)`는 사전의 키이고 자기 라벨(`전교과 2/4/4`)을 갖는다(§4.3).

     > 6판은 여기에 「**비 접미사를 떼고** 라벨을 찾아 다시 붙인다」고 적었다.
     > **반영비가 사전 항목이 아니던 때의 조건이고, 7판이 그것을 바꿨다.** 그대로
     > 구현하면 접미사를 떼어 `전교과`를 찾고 라벨에 `(2/4/4)`를 **다시 붙인다** —
     > 화면 이름이 사전의 라벨이 아니라 **합성한 글자**가 되어 목표 2가 깨지고,
     > 사전에 적은 반영비 라벨 20여 개가 **아무도 읽지 않는 글자**로 남는다.
     > 더구나 그 합성 라벨에는 **괄호가 든다** — 검사 2는 사전만 훑으므로 잡지 못하고,
     > 6단계 전이면 `student.js:315`의 괄호 함정(4차 감사가 잡은 그 사고)에 걸린다.
6. **글자 보고 판단하던 자리를 없앤다** (§1.1의 표 여섯 줄). **「줄인다」가 아니라
   「없앤다」다** — 여섯 자리 전부가 사전 조회로 바뀐다.
   - `registry.js:249`의 `/^gpa\.(전교과|전과목)$/` → 사전의 `default: true`
     (§2.2의 사전순 대표 선택 문제가 함께 사라진다).
     **폴백은 그대로 둔다** — 오늘은 `find(정규식) ?? [값 많은 순][0]`이다. `find`만
     바꾸고 폴백을 빼면 **`전교과` 계열이 실리지 않은 양식**(사전에는 `default`가 있지만
     그 열이 없는 양식)에서 `primaryGpaField`가 `undefined`가 되어 `defaultColumns`가
     내신 열을 빼고 **표가 내신 없이 열린다.** 채워진 `default`가 없으면 지금처럼 값이
     가장 많은 열로 되돌아간다.
   - `student.js:315`의 `label.includes('(')` → `entry.primary`.
   - `student.js:314`의 `['전교과','전과목','전교과목']`과 `조합순` → 사전의 순서.
   - `student.js:256`의 `AREA_ORDER` → 사전의 `areas` 순서.

   **6판은 여기서 「`student.js:315`의 판정은 없어지지 않는다 — 반영비는 열거할 수 없는
   열린 값이라 사전으로 물어볼 수가 없다」고 적었다. 틀렸다.** §4.3이 열거했다. 반영비를 열거하기로 한
   순간(§4.3) 물어볼 수 있게 됐다. 열거를 피하려고 규칙을 두었고, 규칙이 있으니 그
   규칙을 보는 코드가 필요했고, 그 코드가 또 글자를 해석했다 —
   **한 번 해석하기로 하면 해석이 번진다.**

   **`student.js:303-313`의 주석도 함께 고친다.** 지금은 「나누는 기준은 **괄호**다.
   조합 이름은 학교마다 다르므로 이름을 목록으로 박아 두면 다른 학교에서 통째로
   빗나간다」고 적혀 있다. 조합 이름이 자유 문자열일 때는 맞는 판단이었지만 **그 전제가
   이 설계로 사라진다.** 주석을 고치지 않으면 다음 사람이 그 근거를 읽고 괄호 판정을
   되살린다 — §8(주석은 **왜**를 적는다)이 그래서 있다.

   **검사 2의 괄호 조항 근거도 다시 적는다** — 「`student.js:315`에 걸린다」가 더는
   참이 아니다. 「라벨은 글자 판단의 입력이 아니다」로 바꿔 적지 않으면 다음 사람이
   「이제 괄호 써도 되네」로 읽는다.
7. **회귀 테스트** — 검사 4·8·9·10·11, 그리고 **격자로 바꾼 검사 5**(§7-5).
8. **`backlog.md`에 두 줄** — (가) 배포 전에 `pruneView`의 말없는 버리기를 다시
   본다(§6). (나) **실데이터를 처음 실행하는 날 §10의 확인 거리를 센다** — 반영비가
   이름의 과목 순서에 묶여 있지 않은지, 같은 코호트를 두 양식으로 내보내 **행 수만**
   센다(값은 한 건도 내보내지 않는다, §1). **이 설계가 유일하게 추측 위에 서 있는
   자리**이고, 그날이 지나면 아무도 다시 묻지 않는다.

1과 3은 떼어낼 수 있다. 2·4는 묶여 있다. 5·6은 4 뒤에 온다.

| 조합 키 표기 | **수능 영역 순서 고정** (국·수·영·사·과) | 자료 밖의 기준이다. 불투명 id는 쓰지 않는다 — 프로파일 JSON은 사람이 눈으로 감사하는 파일이라 `gpa.c7`은 §4의 「사람이 확인한 답」을 읽을 수 없게 만든다 |
| 합치기의 선 | **토큰 다중집합이 같고 순서만 다른 것만** | §4.1 |
| 반영비 | **규칙을 만들지 않고 열거한다** | 사용자 결정. 양식을 알고 있으므로 해석할 이유가 없다 (§4.3) |
| 코드의 열 이름 해석 | **전수로 없앤다 — 사전 조회로** | 사용자 결정. 「나누는 기준」이 곧 해석이다 (§1.1) |

## 10. 남겨 두는 확인 거리 하나

**반영비가 이름의 과목 순서에 묶여 있지 않은가.**
`국영수사(2/4/4)` ≡ `국수영사(2/4/4)`를 합치는 것은 **비의 자리가 이름의 과목 순서를
따르지 않는다**는 전제에 서 있다. 네 과목에 숫자가 셋이므로 과목별 위치 지정은 아닐
가능성이 높지만 — **확인한 것은 아니다. 추측이라고 적어 둔다.**

확인하려면 같은 코호트를 두 양식으로 내보낸 자료에서 두 열의 값이 일치하는 **행 수만**
세면 된다. 값은 한 건도 내보내지 않는다(§1). D23이 분포로만 검증한 그 방식이다.

**노출 범위는 좁다.** 이 전제가 걸리는 것은 **반영비가 붙은 키뿐이다** — 전체 반영 열은
비가 없어 전제가 필요 없다. 전제가 깨지면 **그 변형들만** 다시 나누어 두면 되고,
설계 전체를 다시 확인할 일이 아니다.

§2.4의 관찰(한 파일 안에서 순서가 흔들린다)이 이 전제를 간접적으로 받쳐 준다 —
양식을 만든 쪽이 순서를 뜻으로 쓰고 있다면 한 파일 안에서 흔들 수 없다.

### 사용자 결정으로 (8판) — 해석하는 자리를 전수로 없앴다

**「`나누는 기준`이라는 것 자체가 열 이름을 코드가 해석하고 있는 거다. 애초에 우리는
진학 프로그램 엑셀 양식을 알고 있으니, 해석하는 게 아니라 미리 사전에 정의해 두는 게
옳은 방향이다.」**

7판의 원칙을 코드 전체로 넓혔다. **§1.1을 새로 두고 해석하는 자리를 전수로 찾았다 —
여섯이다.** 전부 사전 조회로 바뀐다.

- `student.js:315` `label.includes('(')` → 사전의 **`primary`**
- `student.js:314` `['전교과','전과목','전교과목']` + `startsWith` → 사전의 순서
- `student.js:256` `AREA_ORDER` → 사전의 `areas` 순서
- `registry.js:249` `/^gpa\.(전교과|전과목)$/` → 사전의 **`default`**
- `registry.js:68` 키를 쪼개 라벨 만들기 → 사전의 `label`
- `isKnownFieldKey` 정규식 → 사전의 키 집합 소속

**학생 지원 모달의 기본 표시를 사전이 정한다** — `primary` 13개가 보이고 반영비 16개는
접힌다. **사전에 없는 고유키는 내신 묶음에 아예 뜨지 않는다**(`extra`로 간다).
「반영비 없음 == 기본 표시」는 오늘의 우연이므로 **규칙으로 두지 않았다.**

**작업 순서 6단계가 「줄인다」에서 「없앤다」로 바뀌었다.** 6판은 그 자리에서
「`student.js:315`의 판정은 없어지지 않는다 — 반영비는 열거할 수 없는 열린 값이라
사전으로 물어볼 수가 없다」고 적었는데 **틀렸다.** 열거를 피하려고 규칙을 두었고,
규칙이 있으니 그 규칙을 보는 코드가 필요했고, 그 코드가 또 글자를 해석했다 —
**한 번 해석하기로 하면 해석이 번진다.** `student.js:303-313`의 주석도 함께 고친다
(그 근거를 읽고 다음 사람이 괄호 판정을 되살린다).

해석을 남기는 자리는 **둘뿐이고 둘 다 「모르는 열」을 다룬다** — `isIdentityLabel`
(§1 위반이 손해라 느슨해야 한다)과 스칼라의 `affix`·`partial`(모르는 프로그램용 그물).
**대상이 미지일 때만 해석하고, 아는 양식은 사전에 적어 둔다**가 기준이다.

검사 16~19를 더했다(사전에만 있는지 소스로 확인, `default`가 정확히 하나,
`primary`가 반영비 키에 없음, 학생 레코드의 `gpa` 키가 전부 사전에 있음).
검사 15의 `⊆` 비대칭이 의도라는 것도 적었다.

### 사용자 결정으로 (7판) — 반영비 규칙을 버렸다

**「엑셀의 열 이름은 곧장 받아들여야지, 정규화해서는 안 된다. 프로파일에 있는 양식은
어떤 의미인지 전부 알고 있으니, 세부 변동 조건을 만들 필요 없이 미리 계산해 두면 된다.」**

맞는 지적이고, 이 설계에서 가장 큰 수정이다. 1~6판은 반영비를 **읽는 규칙**을 쌓고
있었고 감사 세 차례가 그 규칙의 버그를 고치고 있었다. §4.3을 통째로 갈아
**41가지를 29개 고유키로 보내는 표**로 바꿨다. 함께 사라진 것:

- 숫자를 뽑아 `/`로 잇기 → `(5등급)`에서 **없는 비를 지어내던 자리**(5차 감사)
- 구분자 통일 → 본 적 없는 `2:4:4`를 미리 다루던 자리(2차)
- 전체 반영 판정 → `(100)` 변형을 함께 열거하니 **판정 자체가 없어졌다.**
  순서를 안 적어 빈칸·`100%` 열이 떨어지던 6차 지적이 **발생하지 않는다**
- 소수점 허용 문자 → `1.5/2` 거절 모순(6차)
- 비 정규식 → `gpa.전교과(100)`·`gpa.전교과()`가 유효 키가 되던 자리(4차)
- `isKnownFieldKey`의 쪼개기 → **사전의 고유키 집합 소속 판정 한 줄**이 되었고,
  프로파일 경로의 문지기로서 어떤 규칙보다 세다

검사 10을 「반영비에 점이 든 키도 통과」에서 **「사전의 고유키 집합과 정확히 같은 것만
받는다」**로 바꿨다. 검사 2의 괄호 조항은 「키의 괄호는 반영비 접미사뿐」로 정리했다 —
이제 반영비가 사전 항목이므로 키에 괄호가 있다.

### 5차 감사 지적으로 (6판)

- **비로 읽는 조건을 「숫자와 구분자만으로 된 글자」로 좁혔다** (§4.3).
  5판의 「숫자만 뽑아」는 `(5등급)`에서 **`gpa.전교과(5)`라는 없는 반영비를 지어냈다** —
  §5를 정면으로 어기는 자리다. D18이 이 양식에서 `(5등급)` 열을 실제로 만났다고
  적어 두었고, 오늘 등록한 `kcue-2027`의 머리글에도 `(9등급)`·`(5등급)`이 있다.
  값이 1~5라 교차검증도 통과하고, 6단계 뒤의 반영비 판정이 그 열을 접힌 서랍에 숨긴다.
  괄호가 둘인 머리글도 이 한 구절로 함께 막힌다.
- **검사 12를 `⊆`에서 `==`로 고쳤다.** `⊆`는 §4.6이 막겠다고 적은 실패(「표기를
  `gpaCombos`에만 더한다」)를 **그대로 통과시킨다** — 사전 쪽이 커지는 방향이기 때문이다.
- **「구역 판정의 앵커 비교는 `base`를 계속 쓴다」를 §4.3에 적었다.** 소절 제목이
  「`base`로 하지 않는다」라서 `findSections`까지 함께 걷어내는 것이 자연스러운 오독이고,
  그러면 **한 줄 머리글에서 내신 구역이 아예 열리지 않는다.** 기존 구역 판정 픽스처는
  두 줄 머리글이라 잡아 주지 않는다. 같은 낱말이 두 함수에서 반대 일을 하는 자리다.
- 검사 2의 괄호 문장을 「사전의 키에는 없다 — 반영비는 사전 항목이 아니다」로 정리어
  구현 범위를 분명히 했다.

### 4차 감사 지적으로 (5판)

- **조합 맞추기에 괄호를 걷어낸 `base`를 쓰지 않는다**를 §4.3에 못 박았다.
  기존 `scoreLabel`을 그대로 재사용하면 `전교과(2/4/4)`가 `전교과`에 **정확 일치
  100점**으로 걸려(확인함) 비가 사라지고, 네 열이 한 키를 다투어 셋이 `extra`로 가고,
  **살아남은 2/4/4 가중평균 열이 `전교과`로 이름 붙어 `primaryGpaField`가 그것을 대표
  내신으로 올린다.** 값이 1~9라 교차검증도 통과한다.
  `resolveColumns.js:37-41`의 주석이 이미 「걷어내면 네 열이 한 열이 된다」고 경고하고
  있었다 — **지금 안전한 것은 `gpaKeyOf`가 날것 라벨을 쓰는 우연 덕이고, 4단계가 그
  우연을 걷어낸다.** 이번 판에서 가장 중요한 수정이다.
- **2단계 검사 5에 「프로파일마다 따로」를 적었다.** 글자대로 5장을 모아 실행하면
  **충돌 11가지**가 뜨는데 그것이 전부 이 설계가 하려는 합치기다(확인함). 그 시점에
  고칠 수 있는 것은 사전뿐이라 **가장 쉬운 탈출구가 합치기를 되실행하는 것**이 된다.
  「오늘 실행한 결과: 같은 프로파일 안에서는 5장 모두 충돌 0」을 기준으로 남겼다.
- 검사 1의 키 겹침을 **`combos`+`subjects` 합쳐서** 보도록 넓혔다 — 둘은 같은 `gpa.`
  키 공간에 떨어진다.
- 검사 2에 **키의 괄호 금지**를 더했다 — 6단계가 반영비 판정을 키로 옮기므로.
- 검사 15(`한국사` ⊆ `suneungAreas`)를 더해 12·13·14와 대칭을 맞췄다.
- 검사 4의 `sample-2026` 예시에 「3단계 전이라면」을 붙였다.

### 3차 감사 지적으로 (4판)

- **4단계가 「한 줄 삭제」가 아니라 프로파일 키 38개 재작성이라는 것**을 밝히고,
  **사전으로 실행하는 일회용 스크립트로 표기→키만 바꾸고 열 번호는 손대지 않는다**를
  못 박았다. 규모가 적혀 있지 않으면 구현하는 사람이 막히고, 가장 쉬운 탈출구가
  `isKnownFieldKey`를 느슨하게 되실행하는 것 — 2판이 실제로 그랬던 방향이다 (§8-4).
- **검사 5가 예정된 자리(7단계)에서 빈 검사가 된다**는 것을 알았다. 프로파일은 머리글
  글자를 보관하지 않으므로 키가 정규화되는 순간 검증력이 사라진다. 2단계의 일회성
  감사 + 7단계의 격자 회귀로 나누었다 (§7-5).
- **`국영수사과`를 사전에서 뺐다.** §4.1의 선에는 맞지만 §8-3이 그 표기를 지우므로
  남겨 두면 §1의 「본 것만 넣는다」를 문장 그대로 어긴다. 어떤 양식이 택일 조합을
  슬래시 없이 적으면 **조용히 합쳐진다** (§4.1).
- **`탐1`·`탐2`·`제2외`를 뺐다.** 동봉본에서 관찰된 적이 없다. 바로 아랫줄에서
  `한문`·`탐구I`는 넣지 않는다고 적으면서 이 셋을 넣은 것은 같은 기준을 두 줄에 다르게
  적용한 일이었다 (§4.0).
- 검사 1에 **고유키 중복 금지**를, 검사 6에 **`partTypes`의 값 검사**를 더했다.
- 검사 3에 **네 갈래의 짝**을 명시했다 — 없으면 구현할 수 없거나 조합·영역을 빼놓고
  통과한다 (§7-3).
- §4.3에 비 정규식의 구멍 둘을 닫았다 — **`wholeRatios` 거절**(`gpa.전교과(100)`)과
  **숫자 없는 비**(`gpa.전교과()`).
- 5단계에 **`fieldLabel`이 비 접미사를 떼고 라벨을 찾아 다시 붙인다**를 완료 조건으로
  넣었다. 없으면 같은 조합이 한 화면에 두 이름으로 선다 (§8-5).
- 6단계 뒤에 **검사 2의 괄호 금지 근거를 다시 적는다**를 넣었다. 판정을 키로 옮기면
  원래 근거가 거짓이 되어, 다음 사람이 금지를 풀 빌미가 된다.
- 5단계에 `student.js:306`의 주석을 넣었다 — 물러난 표기가 주석에 남으면 되살아난다.
- 검사 9의 문장을 경로마다 **재는 것이 다르다**로 고쳤다.
- §10에 **전제의 노출 범위**(반영비 붙은 키뿐)를 적었다.
- **숫자를 또 고쳤다**: 조합 종류 17 → **13**(3판의 14는 틀렸다). §2.1의 「12개 남짓」도 맞췄다.

### 사용자 결정으로 (3판)

- `국수영사/과` = **4과목**, 센진학 `국수영사과` = **5과목 전부**. 둘은 합치지 않는다 (§4.1.1).
- `국영수사과`(우리 예시 양식)는 **사전에 넣지 않고 생성기를 `국수영사`로 고친다** (§4.1·§8-3).
- 전과목 평균의 대표 표기는 **`전교과`** (§9).
- 「대교협에 두 필드가 각각 있다」는 근거는 저장소에서 확인되지 않았다. 결론은 유지하고
  **그 사실을 §4.1.1에 적어 두었다.**

### 2차 감사 지적으로 (3판)

- **`repeating`의 모양을 바꾸지 않는다.** `parts`를 객체 배열로 바꾸면 `profile.js:32`가
  깨져 **프로파일 5장이 전부 거절되고**, `partTypes`를 흡수하면 `buildRecords.js:17`이
  깨져 **수능 값이 글자로 저장된다.** 라벨만 더하는 모양으로 고쳤다 (§4.0).
  그래서 2단계의 「코드는 읽지 않는다」가 **진짜로** 성립한다.
- **라벨에서 괄호를 뺐다.** `국·수·영·사/과 (택일)`은 `student.js:315`에 걸려
  대교협에서 가장 자주 보는 조합이 접힌 서랍으로 들어갔다. 검사 2에 넣었다 (§4.0).
- **`isKnownFieldKey` 처방을 뒤집었다.** 2판은 느슨하게 하라고 적었는데 그것은
  **프로파일 경로의 유일한 문지기를 없애는 일**이었다. 키를 쪼개어 조합키는 사전에서,
  비는 숫자 패턴으로 본다 (§4.3). §4.5에 「프로파일 경로는 사전을 거치지 않는다」를 못 박았다.
- **`section-anchors`와 새 사전을 묶는 검사 셋**을 넣고, §4.0 표를 현실에 맞췄다 (§4.6, 검사 12~14).
- **숫자를 고쳤다**: 41 → **29**개, 조합 종류 17 → **14**개. 「약 20개」는 틀렸다 (§4.1).
- **예시 양식을 고칠 표기를 `국수영사`로 지정했다** — 안 적으면 3·4단계가 두 번 고치게 된다 (§8-3).
- `student.js:314`의 `전교과` 목록(셋째 사본)과 5단계의 완료 조건을 넣었다.
- 6단계에서 반영비 판정을 **키를 보게 옮기도록** 고쳤다 (라벨 괄호 함정의 뿌리).
- §4.7의 깨진 출력 줄을 고쳤다.
- §2.4에 **`kcue-2027` 한 파일 안에서 순서가 흔들린다**는 관찰을 넣었다 —
  「순서만 다른 것은 짐작이 아니다」가 추론에서 관찰로 올라섰다.
- §10에 **반영비-순서 전제가 추측이라는 것**과 확인 방법을 적었다.
